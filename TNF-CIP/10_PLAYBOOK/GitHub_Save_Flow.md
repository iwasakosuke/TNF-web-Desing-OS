# GitHub_Save_Flow

TNF-CIPの全アウトプットをGitHubリポジトリにどう保存・記録するかの運用ルール。
Claude_Code_Engineer_AIおよびファイル操作を行うすべてのAI社員が従う。

## 目的

「どの案件の、どのフェーズの、誰の成果物か」が、リポジトリの構造とコミット履歴
だけで再現できる状態を維持すること。属人的な記憶やチャット履歴に依存せず、
GitHub自体が組織の記憶装置として機能するようにする。

## フェーズ

### Phase 1: 保存先の決定
- **担当**: Claude_Code_Engineer_AI
- **やること**: 成果物の種類に応じて保存先を判定する

```
- 案件固有の成果物 → 08_PROJECT_TEMPLATES/{種別}/{クライアント名スラッグ}/
- 汎用化されたDNA・パターン → 03_STYLE_DNA / 04_VISUAL_DNA / 05_UI_UX_SYSTEM /
  06_MOTION_SYSTEM
- 生成画像・ムードボード・参考資料 → 09_ASSETS配下の該当カテゴリ
- プロンプトテンプレート → 07_PROMPTS配下のツール別フォルダ
- 組織運用ルールそのものの変更 → 00_COMPANY_CORE / 01_DIVISIONS / 02_AI_EMPLOYEES /
  10_PLAYBOOK
```

### Phase 2: 命名規則の適用
- **やること**: 下記命名規則に従ってファイル・フォルダ名を決定する

```
- クライアント名フォルダ: 小文字スネークケースの英数字スラッグ
  （例: cafe-verde, acme-corp）
- 案件内ドキュメント: 00_Client_Brief.md のように2桁連番+役割名
  （Delivery_Flow.mdの「納品パッケージ構成」に準拠）
- 画像アセット: {セクション名}-{内容}.jpg 形式（例: hero-exterior.jpg）
- ライブラリファイル: 既存の命名パターン（PascalCase + _DNA.md 等）を踏襲し、
  新規カテゴリを作る場合はStyle_DNA_Manager_AIの承認を得る
```

### Phase 3: コミット
- **担当**: Claude_Code_Engineer_AI（または操作を行った各AI社員）
- **やること**: 下記コミットメッセージ規約に従い、フェーズ単位でコミットする
  （1コミットに複数フェーズの成果物を混在させない）

```
コミットメッセージ規約:
- 1行目: 「〜を追加」「〜を作り込み」「〜を更新」等、変更の要約(日本語)
- 空行
- 本文: 何を・なぜ変更したかを2〜4行で説明(背景・目的を含める)
- 末尾: Co-Authored-By署名を必ず付与
```

### Phase 4: プッシュ
- **担当**: Claude_Code_Engineer_AI
- **やること**: 指定ブランチにプッシュする。ブランチ運用は下記ルールに従う
- **完了条件**: プッシュ成功、リモートとの同期確認

## ブランチ運用ルール

- 通常の案件制作・ライブラリ更新は、割り当てられた作業ブランチ
  （例: `claude/{セッション識別子}`）上で行う
- mainブランチへの直接pushは行わない。統合はPull Requestを介する
  （PR作成はユーザーの明示的な指示がある場合のみ行う）
- 案件ごとに新規ブランチを切る必要はない。案件の区別はフォルダ構造
  （08_PROJECT_TEMPLATES配下）で行い、ブランチはセッション単位の作業単位として扱う

## 完了条件（このFlow全体）

- 成果物が正しいカテゴリフォルダに保存されている（Phase 1の判定基準に合致）
- ファイル名が命名規則に準拠している
- コミットメッセージが規約に従い、変更の背景・目的が説明されている
- リモートへのプッシュが完了している

## NG例

```
案件の成果物とライブラリ更新を1つのコミットにまとめ、
コミットメッセージも「更新」の1行のみで済ませる。
```
後から履歴を追う際に、どの変更がどの目的だったか判別できなくなる。
複数の意図が混在したコミットは、後日の切り戻しも困難にする。

## 良い例

```
git commit -m "Cafe Verde案件のHero/Concept/Menuセクションを追加

02_LP_SYSTEM/Cafe_LP.mdの構成に基づき、VERDEブランドの配色・フォントで
Hero/Concept/Menuの3セクションを実装。残りセクションは次コミットで対応。

Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>"
```
1コミットの範囲が明確で、背景（どのドキュメントに基づくか）と
スコープ（残作業の有無）が記録されている。

## 次フェーズへの引き継ぎ

- 本Flowは他の全Flow（Client_Intake〜Delivery）と並行して、
  各フェーズの成果物が生まれるたびに随時実行する
- Delivery_Flow Phase 1（納品パッケージ作成）の完了と同時に、
  最終コミットを実施する
